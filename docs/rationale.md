# 규칙이 왜 그런가 — 원리와 겪은 사고

`CLAUDE.md` 의 규칙이 납득이 안 될 때 편다. **판단에는 필요 없다** — 규칙 자체는 `CLAUDE.md` 에 있고
여기는 그 근거만 있다. 규칙을 바꾸려 할 때 이 문서를 먼저 읽으면 같은 사고를 다시 겪지 않는다.

---

## 1. CSS 파일이 둘(common / override)인 이유 — `@layer`
→ `CLAUDE.md` §2

`index.html` 의 레이어 순서:
```
properties → theme → base → police → components → utilities → screen
```
- `police-style.css` · `police-common.css` → `layer(police)`
- `police-override.css` → `layer(screen)` (utilities 뒤 = 테일윈드·shadcn 을 덮는다)

**`@layer` 비교는 명시도보다 위**라서, `layer(police)` 안에 있는 한 파일 맨 아래에 두든 셀렉터를 아무리
길게 쓰든 `layer(utilities)` 의 한 줄짜리 유틸에게 진다. 그래서 덮어야 하는 스타일은 물리적으로 다른
레이어에 있어야 한다 — 두 파일을 합칠 수 없는 이유다.

`police-style.css` 는 레이어 위치를 옮길 수 없다 — `police > base` 여야 police reset 이 테일윈드 preflight 를
덮고(포털 화면 정상), `utilities > police` 여야 shadcn 이 정상이다.

`police-common.css` 는 `police-style.css` **다음에** import 되므로, 같은 레이어에서 소스 순서가 뒤라 원본과
붙으면 이쪽이 이긴다. 원본을 안 건드려도 덮을 수 있다.

`!important` 는 레이어 순서가 **뒤집힌다** — layered `!important` 가 unlayered 보다 강하다. Tabulator 처럼
JS 가 인라인 style 을 써 넣는 경우 말고는 쓸 일이 없다.

## 2. "화면 전용 CSS → 나중에 승격" 을 없앤 이유
→ `CLAUDE.md` §2

승격 단계가 실제로 작동하지 않았다. 화면ID 프리픽스 `styles.css` 에 146 규칙이 쌓였고, 그중 **중복이
20그룹**, 그중 **6그룹은 이미 공통에 있는 걸 모르고 다시 만든 것**이었다. 2026-09-04 에 전부 `.lp-*` 로
이름을 바꿔 common/override 로 옮기고 `.vue` 124건을 치환하면서 `styles.css` 를 없앴다. 걷어올 게 없으면
실패할 것도 없다 — 그래서 처음부터 공통에 만든다.

`.lp-` 접두사가 필수인 이유: 원본 `police-style.css` 가 `card` `title` `value` `wrap` `note` 같은 범용어
**159개**를 점유하고 있고, 우리 파일이 뒤에 로드돼 우리가 이긴다. 이름이 겹치면 포털 화면(헤더/푸터/공지)이
조용히 깨진다.

카멜케이스 금지의 실제 사고: `PC-LPO-0801` 한 파일에 `.photo-frame` 과 `.photoFrame img` 가 섞여 **둘 다
미매칭**된 채 남았다(2026-09-04 정리).

## 3. `route.ts` 를 폐기하고 `plannedRoutes` 로 간 이유
→ `docs/create.md` §3

882줄짜리 `router/index.ts` 를 화면 추가마다 셋이 동시에 손대서 git 충돌이 상시로 났다. 그래서 화면
폴더마다 `route.ts` 를 두고 자동 수집하게 했었는데, 이 방식엔 **"나중에 걷어오기"** 가 남아 있었다 — 한
사람이 `route.ts` 수십 개를 `index.ts` 로 옮기는 배치 작업이라, **충돌이 없어진 게 아니라 그 시점에 뭉쳐서
터졌다.** 일도 두 번 했다.

`plannedRoutes` 는 그 단계 자체를 없앤다. **목록(화면ID 279개)이 이미 채워져 있어서 새 화면을 만들 때
라우터 파일을 아무도 안 건드린다.** 걷어올 것도 없다.

**리터럴 경로 함정**: `index.ts` 에 `component: () => import('../views/com/PC-COM-9999/PC-COM-9999.vue')`
처럼 리터럴 경로로 적어 두면 Rollup 이 빌드 시점에 정적 분석해서 파일이 없을 때 `Could not resolve ...` 로
**빌드 전체를 실패**시킨다(실측. `vue-tsc` 는 통과해서 넣은 사람은 모르고 배포하는 사람이 막힌다).
`plannedRoutes` 는 `import.meta.glob` 맵에서 꺼내므로 이 함정이 없다. 화면군처럼 `index.ts` 에 직접 적을
때는 함정이 그대로 살아 있다 — 파일을 먼저 만든다.

## 4. LNB 프리셋만은 배치 등록인 이유
→ `docs/create.md` §3

IA 의 depth 는 "화면 계층"이고 LNB 는 "메뉴 구조"라 서로 다르다. IA 로 자동 생성하면 이렇게 틀린다:
```
IA:  장비관리 > 기동장비 탭 / 통신장비 탭 / 무기 탭 …
LNB: 개인장비                       ← 탭은 화면 안에 있지 메뉴 항목이 아니다
IA:  관내현황 > 상세내역
LNB: 관내현황                       ← '상세내역'은 메뉴가 아니다
```
**LNB 구조는 Figma 를 봐야 아는 디자인 결정**이지 IA 에서 유도되지 않는다. 라우터는 화면ID만 알면 되지만
(`plannedRoutes`), 화면 폴더는 자기가 메뉴 트리의 어느 자리에 붙는지 모른다. 그래서 프리셋만은 배치 때
사람이 판단해서 넣는다.

`presets.ts` 에 `path` 가 박힌 화면은 21개뿐인데 화면 폴더는 36개다(2026-09 기준). 나머지 메뉴 항목은
`{ name: '근무일지(甲)' }` 처럼 이름만 있다 — 신규 화면이 라벨로 값을 찾는 게 정상인 이유다.

## 5. 만드는 세션과 검증 세션을 나눈 이유
→ `CLAUDE.md` §0

한 세션이 둘 다 하면 자기 논리를 그대로 다시 따라가서 못 잡는다. 실제로 겪었다: `openIndex: -1` 을
"인사관리는 1뎁스라 펼칠 게 없다"는 주석까지 달아 확신하며 틀렸다(정답은 6). 만든 세션이 스스로
검토했어도 같은 논리를 반복했을 것이다. 인계 메모 3번("확실하지 않은 것")이 두 세션을 잇는 다리다.

## 6. 기준 파일을 유형별로 고정한 이유
→ `docs/create.md` §2

매번 "제일 비슷한 화면"을 새로 판단하면 같은 유형도 화면마다 다른 베이스로 갈라진다 — 20개+ 화면이 그렇게
갈라졌다. 같은 "2분할 목록+상세" 화면인데 한쪽은 `LayoutSplit`, 다른 쪽은 `styles.columns` + `styles.panel`
로 짜인 적도 있다.

기준 파일 정비 이력: 2026-08-31~09-01 에 `PC-LPO-0215`(LNB 추가, 죽은 브레드크럼 링크 제거, 불필요한 래퍼
제거, 페이지네이션 예시 추가), `PC-LPO-0801`(테일윈드 7줄 → 0). 같은 기간에 LNB 활성 표시 오류를 16개
화면에서, 죽은 브레드크럼 링크를 11개 화면 19곳에서 일괄 수정했다. 2026-09-03 에 화면·팝업 62개의 블록
순서를 `<template>` → `<script setup>` 으로 일괄 정리했다.

## 7. 인라인 스타일·테일윈드를 화면에서 금지한 이유
→ `CLAUDE.md` §1

디자인이 바뀔 때 클래스 하나만 고치면 전체 반영되게 하려는 것. 화면마다 흩뿌리면 화면마다 손봐야 한다.
`src/components/**` 재사용 컴포넌트 내부는 예외인 이유도 같다 — 고칠 곳이 한 파일이라 흩어질 문제가 없다.

## 8. 남의 파일과 중복을 합치지 않는 이유
→ `CLAUDE.md` §1

3명이 동시 작업이라 남의 파일을 건드리면 pull 때 충돌이 난다. 중복 제거로 얻는 이득보다 충돌 해소 비용이
크다. `PM-PUB-0409` 의 `regionOptions` 와 `views/pub/composable/drunkCenter.ts` 가 그 예 — 합치지 않고 뒀다.


## 치수는 시안에서 재고, 기준 파일 값은 복사하지 않는다 (2026-09-14)
PM-COM-0402(Q&A 상세)를 PM-COM-1002 를 기준으로 만들면서 `.lp-notice-detail { gap: 2rem }` 을 그대로
썼다. 시안은 배지→제목 12, 제목→메타 32, 구분선→이미지 40/32, 본문→파일 32 처럼 블록마다 다른데
전부 20 으로 나갔다. 원인은 셋 — `get_design_context` 의 바깥 프레임 `gap` 만 믿고 좌표를 안 잰 것,
기준 파일의 픽셀값을 검증된 값으로 취급한 것, 마무리를 "비슷해 보인다" 로 끝낸 것. 그래서 §4 에
치수 측정 단계를, §5 에 숫자 대조를 넣었다. 컴포넌트 내부 치수(`DateRangePicker` 8px 간격 등)와
시안이 갈리는 경우는 규칙으로 없어지지 않아 "알리고 결정받는다" 로 남겼다.
